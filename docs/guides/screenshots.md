# Public screenshots (for contributors)

The images in `docs/images/screenshots/` are shown in the README, the guides and on GitHub. They must show the real,
current application with synthetic data only. They are regenerated by the browser tests, never edited by hand,
upscaled or mocked.

## How they are made {#capture}

`scripts/e2e.sh` builds a throw-away instance with synthetic demo data and then runs these scripts:

| Script | What it does | Public screenshots |
| --- | --- | --- |
| `flow.mjs` | first-run setup, a synthetic passport scan marked "NOT A REAL PASSPORT", users | — |
| `parity.mjs` | synthetic folders, file types, imports, notifications, security… | most images used by the guides |
| `screenshots.mjs` | — | README story, offline access, themes, security/sign-in records, phone |

`screenshots.mjs` writes `docs/images/screenshot-manifest.json` with the caption, source and size of each of its
images. To refresh the images:

```bash
createdb pd_e2e   # an empty database
PD_DB_NAME=pd_e2e scripts/e2e.sh
git add docs/images/screenshots docs/images/screenshot-manifest.json
```

When `pngquant` is installed, the images are recompressed losslessly enough for text (quality 85–98).

## Rules every capture follows (automated) {#rules}

- **Size:** desktop 1440 × 900 CSS pixels and phones 390 × 844, both at device pixel ratio 2 (sharp on high-DPI
  screens). The old images were 1× and mixed 1366/1440 widths.
- **Settled:** taken after fonts have loaded, images have decoded and loading placeholders are gone. Animations are
  off (reduced motion) and toasts are removed.
- **Quality gate:** the capture fails on sideways page overflow, clipped headings/buttons/badges/labels, or broken
  images.
- **Privacy gate:** the capture fails if the visible text contains any of these:
  - an e-mail address outside `example.com/.org/.net`, `family.example`, `.test` or `.invalid`;
  - a public IP address outside the documentation ranges (192.0.2.x, 198.51.100.x, 203.0.113.x). Loopback and private networks (`10.x`, `172.16–31.x`, `192.168.x`, as used by Trusted Zones) are allowed;
  - a token-like string of 40+ characters (names made of words joined by - or _, such as long file names, are not tokens).
- **Demo data only:** documents are generated (`tests/fixtures.py`, `tests/e2e/make_parity_fixtures.py`) and say they
  are samples. The family names are the demo identities. No real passport, ID, Iqama, bank or medical scan may ever be
  used, even blurred.

## Review before publishing {#review}

Look at every changed image (the CI artifact *e2e-screenshots* has them) and check:

- **Text:** baselines, no clipping or overlap, readable size, no distorted typography.
- **Alignment:** icons, badges and buttons line up; cards and tables are aligned, with even spacing.
- **Crop:** intentional crop, no half-visible dialogs or menus, sensible whitespace, no stray scrollbars.
- **Accuracy:**
  - the state shown is real and consistent (no error toasts or half-loaded lists);
  - the feature shown exists;
  - the caption is accurate.
- **Privacy:** synthetic data only; no private names, domains, identifiers, IP addresses or notification destinations.

## README story {#story}

The README shows the product in this order:

1. Overview
2. Folders and documents
3. Viewer
4. Offline access and the installed app
5. OCR
6. Notifications
7. Security (including the sign-in map)
8. Backup & Recovery
9. Themes

Keep captions short and factual. Images that only explain a concept (none today) must be labelled
"Conceptual illustration".

### Documentation screenshots (Change Set T) {#guide-shots}

Step `AT-333` of `tests/e2e/screenshots.mjs` captures the screenshots used next to the steps in the guides:

| Images | Guide |
| --- | --- |
| `backup-overview`, `backup-policy-dialog`, `backup-destination-dialog`, `backup-points`, `backup-key`, `backup-stepup`, `backup-delete-dialog`, `recovery-explorer`, `recovery-impact` | Backup and restore |
| `notifications-routing`, `notifications-channels`, `admin-delivery-health` | Notifications, Discord |
| `security-trusted-zones`, `security-signin-map`, `security-devices` | Sign-in security and map |

Step `AT-354` (Change Set U) captures:

| Images | Guide |
| --- | --- |
| `folders-tree` | Getting started (folder tree) |
| `security-map-provider`, `security-map-unavailable` | Sign-in security and map (provider, Map unavailable) |
| `connections-whatsapp` | WhatsApp Personal (bridge service) |
| `settings-login-design` (recaptured with the live preview) | Sign-in page designs |

The two map captures answer tile requests locally (a working tile, then HTTP 403), so they never depend on a real
provider. The WhatsApp capture shows the fake bridge used by the tests; no QR code is captured.

They follow the same rules as the README images, plus:

- **Recovery Key:** the key dialog is captured masked. The step-up dialog is captured empty.
- **Destinations:** destination paths are synthetic (for example `/srv/backups/personaldocs`). No real NAS or cloud location appears.
- **Notifications:** webhook addresses are masked. No WhatsApp QR code or session data is ever captured.
- **Sign-in map:** public sign-in addresses come only from the documentation ranges (`203.0.113.0/24`, `198.51.100.0/24`), with
  private Trusted Zone networks.

The map shows real OpenStreetMap tiles. Their attribution stays visible. Behind an HTTPS proxy (`HTTPS_PROXY`) the
capture browser uses the proxy for the tiles. If the proxy re-signs TLS, set `PD_E2E_PROXY_CA` to its CA certificate:
Chromium then trusts exactly that key, and certificate checks stay on.

`scripts/check_docs.py` fails when a guide references a missing image, an image has no alt text, or a screenshot is not
used by any document.

## Sources of the current images {#sources}

All images in `docs/images/screenshots/` are captures of the real application with synthetic demo data. There are no
conceptual mock-ups. `docs/images/social-preview.png` is a composed banner: its window contents are real captures,
with demo data only. `docs/images/layout/` holds before/after captures from the layout audit.
